# Security & correctness audit — Kalshi-Bot

Audited 2026-08-27 against commit `f3dc858` (the public `main`).
Scope: the whole repository, static review plus live Kalshi API verification.

---

## CRITICAL

### C1 — Kalshi API private key published to a public GitHub repo

The files `API` and `API.txt` each contained a Kalshi key ID and the
**complete RSA private key** in plaintext, committed 2026-02-20 and public since.

Anyone who found the repo could sign requests as the account owner: read
positions, place orders, and move the balance. GitHub search and automated
secret scrapers index public repos continuously, so exposure should be assumed,
not hoped against.

**Remediation, in order:**
1. **Revoke the key in Kalshi.** This is the only step that closes the hole. (Confirmed still live on 2026-08-28 before revocation.)
2. Issue a new key; enter it in the dashboard, where it is encrypted at rest.
3. Purge history (below) and/or make the repo private.

Deleting the files is not sufficient — every prior commit still contains them.
Both files are now removed and `.gitignore` blocks `API`, `API.txt`, `*.pem`,
`*.key`, and `.env`.

History purge:
```bash
pip install git-filter-repo
git filter-repo --invert-paths --path API --path API.txt --force
git push --force --all
```
This rewrites every commit hash. Rotation still comes first: a revoked key
makes the leaked copy worthless, which is the actual goal.

### C2 — Hardcoded encryption key in `docker-compose.yml`

`ENCRYPTION_KEY=BivCVHeSDq9rBw3agMgdImjGSzHrb2Yr2aVdqZJRbkE=` was committed. It
is the Fernet key protecting the stored Kalshi credentials, so the "encrypted"
credentials were decryptable by anyone with the repo. `SECRET_KEY` was the
literal string `change_this_to_random_string_production`, making session cookies
forgeable — an attacker could mint an authenticated session without the password.

**Fixed.** Both now come from an uncommitted `.env` generated by
`scripts/bootstrap_secrets.py`. The app raises at import if either is missing,
so it cannot boot insecurely.

### C3 — Default credentials `admin` / `admin123`

`init_db()` seeded that account on every fresh boot. Combined with C2's fixed
`SECRET_KEY`, the app was effectively open to the internet on port 80.

**Fixed.** The user table is gone. Authentication is one bcrypt-hashed
passphrase in the environment, matching the invite-only design: one password
box, no username, no signup, no reset.

## HIGH

### H1 — The bot could never place a trade

`execute_trade()` logged `"PLACING LIVE ORDER"` and returned
`{"status": "success"}` **without calling Kalshi at all**. The UI reported
filled orders that did not exist. Worse, no request in the codebase was ever
signed, so every private endpoint would have returned 401 regardless.

**Fixed.** `kalshi_client.py` implements the required RSA-PSS/SHA256 signature
over `timestamp_ms + METHOD + path` with the three `KALSHI-ACCESS-*` headers.
Verified live: public market and orderbook endpoints return real data;
unsigned private calls fail as expected.

### H2 — No arbitrage logic existed

Despite the name, `_run_loop` fetched markets and logged three tickers. There
was no spread calculation, no fee model, no comparison. `Notes.txt` described
the intent; no code implemented it.

**Fixed.** `arbitrage.py` implements the YES/NO cross-spread and the
mutually-exclusive event basket, both net of the real Kalshi fee schedule.

### H3 — Fee model absent, so "profit" was fictional

Kalshi charges `ceil(0.07 × C × P × (1-P))` dollars, ~1.75c per contract near
50c. A naive scanner reports a 1c gross spread as profit; after fees it is a
~2.5c loss per pair. Every "opportunity" near mid-price would have lost money.

**Fixed.** Fees are computed per leg and subtracted before an opportunity is
reported. `test_rejects_when_fees_eat_the_edge` asserts a 99c pair is rejected.

### H4 — Ask price derived incorrectly (would have inverted the edge)

Kalshi's orderbook returns resting **bids** for each side. The cheapest way to
buy YES is to cross the NO bids: `ask_yes = 100 - best_no_bid`. Treating the
`yes` book as an ask understates cost and manufactures phantom arbitrage.

**Fixed** in `_best_ask()`, with tests pinning both directions.

### H5 — Client-controlled trade parameters

`/api/bot/trade` took an arbitrary `ticker` from the request body and sized the
order from config. Any authenticated session — or any CSRF victim, since there
was no CSRF protection — could trade any market on the account.

**Fixed.** The endpoint takes an `opportunity_id` referring to a server-side
opportunity the engine itself detected and sized. Unknown or expired ids are
rejected.

### H6 — No CSRF protection on any state-changing route

`/api/config`, `/api/bot/start`, `/api/bot/trade`, and `/api/update_password`
were plain cookie-authenticated POSTs. A malicious page visited in the same
browser could change limits, disable dry-run, or trigger trades.

**Fixed.** A session-bound token is required on every non-GET request outside
the login route.

### H7 — Source code mounted as a writable volume

`volumes: - ./web:/app` meant the running container executed host files. Any
write access to that directory changed the trading logic live.

**Fixed.** Code is baked into the image; only `/app/data` is a volume.

### H8 — Plaintext HTTP with no TLS

Nginx listened on port 80 only. The passphrase and session cookie crossed the
network in the clear, and the pasted PEM private key with them.

**Fixed.** Caddy terminates TLS with automatic certificates; the app container
exposes no host port. HSTS is set.

## MEDIUM

### M1 — No risk controls despite config fields for them

`max_exposure`, `min_liquidity`, and `min_profit_pct` were stored and never
read. `max_bet_amount` was read only to print it in a log line. There were no
circuit breakers, no daily loss limit, and no order cap.

**Fixed.** `risk.py` enforces per-trade, exposure, daily-loss, and order-count
limits; trips a breaker on 5 consecutive errors; and stops the engine when
halted. 10 tests cover it.

### M2 — Partial fills could create naked directional positions

Multi-leg arbitrage that fills one leg and misses the other is no longer a
hedge — it is an unintended bet, at size.

**Fixed.** Legs are fill-or-kill limit orders. If a later leg fails after an
earlier one filled, the bot records a partial, **halts**, and asks for manual
unwind rather than looping.

### M3 — Stale prices at execution

The original code re-fetched nothing before "trading," and its own comment
admitted the orderbook fetch was missing. Prediction-market books move in
seconds.

**Fixed.** `_revalidate()` re-fetches the orderbook and recomputes the edge
immediately before sending; if it has vanished, no order goes out.

### M4 — Unbounded input, no validation

`/api/config` wrote any string to any key it recognised. `/api/update_password`
accepted `None` and would have hashed the literal string. Numeric fields were
never validated, so `max_bet_amount = "abc"` crashed the engine mid-loop.

**Fixed.** Keys are allowlisted, numerics are range-checked, the PEM is
sanity-checked, request bodies are capped at 256 KiB, and the password route is
gone with the user table.

### M5 — `threading.Thread` without a stop signal

`stop_bot()` set a flag then `join(timeout=2)`, but the loop slept 10 seconds —
so stop returned "Stopped" while the bot kept trading. Two rapid starts spawned
two loops on one account.

**Fixed.** A `threading.Event` interrupts the sleep immediately; start and stop
are guarded by a lock; join waits 10s.

### M6 — Bare `except:` swallowed decryption failures

In `get_db_config()`, a failed decrypt set the credential to `None` silently, so
a rotated `ENCRYPTION_KEY` looked like "no credentials" instead of an error.

**Fixed.** `InvalidToken` is caught specifically and logged with the actual
cause and remedy.

### M7 — SQLite connections leaked on exception

Every handler called `conn.close()` on the happy path only. An exception between
open and close leaked the handle; under `timeout=10` this surfaces as random
"database is locked" failures.

**Fixed.** `try/finally`, plus WAL mode.

### M8 — Missing security headers, and the login page was indexable

No CSP, HSTS, `X-Frame-Options`, or `noindex`. A private trading terminal should
not appear in search results.

**Fixed.** All set globally, plus `X-Robots-Tag` and a meta robots tag.

## LOW

- **L1** Python 3.9 base image, unpinned dependencies → now 3.12 with floors.
- **L2** Container ran as root → now uid 10001 with `no-new-privileges`.
- **L3** `restart: always` masked crash loops → `unless-stopped`.
- **L4** Duplicate `API` / `API.txt` doubled the leak surface → both removed.
- **L5** Login enumerated nothing useful but had no rate limit → throttled.
- **L6** No healthcheck → added.
- **L7** `version: '3.8'` in compose is obsolete → removed.
- **L8** Log buffer of 200 lines truncated fast → 500, level configurable.
- **L9** No trade history persisted → `trades` table records every attempt.
- **L10** `bcrypt` was only a transitive dep → pinned explicitly.

## Verification performed

- 27 unit tests pass: fee model, ask derivation, spread and basket detection,
  all risk limits, throttle behaviour.
- App boots and serves; unauthenticated `/dashboard` redirects, `/api/*` → 401.
- Wrong passphrase → 401; correct → session; throttle engages after 5 failures.
- POST without CSRF token → 403; with token → succeeds.
- Missing secrets → refuses to start (verified).
- Invalid numeric and PEM input → 400 with a specific message.
- Trade with absent or unknown `opportunity_id` → rejected.
- Live Kalshi API: public markets and orderbooks return data; unsigned private
  call fails as designed.

## Not fixed — needs your decision

1. **Revoking the leaked key.** Only you can do this. Nothing else matters first.
2. **History purge / repo visibility.** Say the word and I will run
   `git-filter-repo` and force-push, or you flip the repo private.
3. **Settlement-based P/L.** `record_settlement` exists but nothing polls Kalshi
   for resolved positions yet, so realized P/L stays 0 until that loop is added.
   Straightforward once a valid key is in place.
4. **Whether real arbitrage exists at your size.** The machinery is correct now;
   whether it clears fees often enough on the markets you care about is an
   empirical question. Run dry-run for a few days and the log will answer it.
